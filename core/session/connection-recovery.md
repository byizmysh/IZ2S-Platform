# Connection recovery: RUN20 and historical protocol notes

The default IZMYSH engine uses the standard bootstrap and cannot resume its native control connection. RUN20 also exposes the separate, opt-in `izmysh-resume` experiment. It reuses the existing NS2R source byte for byte, under its own NS2R save name. It has not yet been installed or qualified on the RUN20 console. Selecting this engine does not upgrade an already running standard session.

The NS2R listener requires protocol 2 and rejects a standard protocol 1 bootstrap. Its pinned source and provenance are recorded in `engines/izmysh-resume/provenance.json`; physical source files remain under `bootstrap-chain/sources/engines/izmysh-resume/`. The ordinary engine is unchanged. The source's retry loop is finite: 120 attempts with 30 VSYNC between attempts, plus connection time. The PC transport retains a 120-second grace period and a 30-second stalled-route probe. These are separate limits, not a guarantee of recovery after every two-minute outage.

Eight RUN20 host tests cover source pinning, refusal to downgrade protocol, cached executed responses, partial requests, silent route loss, replacement of a stale live route after the source IP changes, panel readiness while reconnecting, and the complete launcher RPC bridge. In the bridge test, a write executes before its reply is lost. The same HTTP client resumes the pending write from the cached response and reads all 64 KiB of application RAM; the write executes once, and unrelated RAM remains unchanged. In the address-change test, an invalid receipt cannot close the existing route; an accepted receipt from a second loopback IP replaces it and permits the next native command. These use local TCP peers and do not establish physical airplane-mode recovery. During reconnection, the panel holds new module commands until the link returns and a fresh runtime observation is available. A new SmileBASIC process cannot resume an old session.

Current host evidence: `data/run20-validation/ns2r-main-control-current.log`. Bootstrap identity was rechecked against the RUN13 source after the user's instruction to keep it unchanged. No source-entry or SAVE operation was sent to the console for this experiment. The existing saved console NS2R has not yet been identified; local source identity does not establish its contents.

On 25 October 2026, an experimental protocol 2 bootstrap tracked the last executed command and cached its response. A lost response could be returned without repeating a completed operation. Partial packets were assembled before execution. A stalled transport was detected after 30 seconds; the same SmileBASIC process could reconnect within 120 seconds. Restarting SmileBASIC or the console created a new process and invalidated the old native addresses.

Historical console tests deliberately closed the host TCP socket and separately stalled its reads. Cached replies returned after 4 ms and 93 ms after detection respectively, and the existing menu continued responding. These were transport tests, not physical Wi-Fi reconnection measurements. The user later explained that observed access-point disconnects accompanied manual console restarts; they did not prove spontaneous driver failures.

The historical experimental installer wrote a separate NS2R, verified complete readback and preserved NS2. That experiment does not justify substituting modified source under an unchanged save name. Current installation uses each engine's exact bootstrap and explicit LIST/SAVE slot recipe. An existing NS2R program must be preserved before installing the experimental copy.

A normal package cannot install or replace a system Wi-Fi driver from SmileBASIC. Available networking APIs use system NIFM/WLAN services. Stream transport recovery and native control-session recovery are separate features.

References: [NIFM](https://switchbrew.org/wiki/Network_Interface_services), [WLAN](https://switchbrew.org/wiki/WLAN_services), [SmileBASIC save format](https://github.com/plutooo/smilehax/blob/master/scripts/make_script.py).
